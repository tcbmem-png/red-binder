# Red Binder — Move to Claude Code + Git, Lovable as deploy-only

Playbook. June 17, 2026.

> **Superseded — read `rebuild/architecture-canonical.md` first; it is binding.** This playbook predates two locked decisions. (1) **Client-side only, nothing stored** — the Supabase backend below is removed; PDFs generate in the browser and download directly. (2) **Monorepo + Vercel, Lovable dropped entirely** — it is NOT one Vite app and Lovable is no longer the deployer. The real structure is a pnpm + Turborepo monorepo: `packages/engine` + `packages/templates` + `apps/poa` + `apps/detention-card`, each app its own Vercel project. **Ignore "Step 1 — Give this to Lovable" below and the single-app framing** — repo setup is the scaffold described in the canonical doc (POA session scaffolds). The Claude Code prompt *sequence* (states.ts → tile map → engine routing → templates) is still valid, but it now targets `apps/poa` against the shared `packages/engine`.

## The shape of the move

Lovable creates the GitHub repo and runs two-way sync on `main`. Every Lovable prompt commits to `main` through a bot. So we let Lovable make the repo once — that also lands your current code in Git as the bootstrap reference — and from then on Claude Code owns `main`. You stop sending Lovable build prompts. Lovable keeps watching `main` and deploys. That's the whole arrangement.

```
Claude Code (local)  →  git push main  →  GitHub  →  Lovable Cloud auto-deploy  →  redbinderproject.org
        ↑                                              (no backend — client-side only)
   you + Claude do all building here
```

Two rules that keep this clean:

1. **One writer on `main`.** After the repo exists, do code only in Claude Code. Don't prompt Lovable to change code — its bot also commits to `main` and the two will collide. Treat Lovable as a deploy button, nothing more.
2. **Keep the stack Lovable can deploy.** Vite + React + TypeScript + Tailwind + shadcn/ui + Supabase. This is not Claude being limited — it's so Lovable Cloud keeps deploying without us re-platforming to Vercel/Netlify. If we ever outgrow Lovable's deploy, GitHub → Netlify/Vercel is the fallback and costs nothing to switch to.

Backend decision: **there is no backend.** (This supersedes the earlier "keep Supabase" plan.) The rebuild is client-side only — the browser collects form data, fills templates, generates PDFs with `pdf-lib`, and downloads them. Nothing is stored, nothing is uploaded, nothing is logged. The old Supabase tables, the `free-plan-pdfs` bucket, the Edge Functions, the signed URLs, and the server-side rate limit all get removed, not migrated. See the canonical doc for the full posture and the shared-engine contract.

### Prompt 1 — The state data as single source of truth

> Build the keystone data layer. I have a 50-state + DC research matrix (in `research/poa-portability-matrix-50-state.xlsx`) that classifies each jurisdiction. Encode it as a typed, single source of truth that drives BOTH the map UI and the document engine.
>
> Create `src/data/states.ts` exporting a typed array of all 51 jurisdictions (50 states + DC). Each entry has: `code` (e.g. "MS"), `name`, `tile` (row/col coordinates for a tile-grid cartogram), `documentPath` (enum), `financialExecution` (witness/notary minimum, short string), `medicalExecution` (short string), `upoaa` (boolean | "unconfirmed"), `uhcda` (boolean), `specialTriggers` (string[] — e.g. burial/cremation extra formalities), and `notes`.
>
> `documentPath` enum, three values — this is what the map colors and what the engine routes on:
> - `UNIVERSAL` — UPOAA / portability-friendly states. Engine outputs the universal UPOAA-based financial POA + universal advance directive.
> - `UNIVERSAL_PLUS_ADDENDUM` — own-statute or quirk states (e.g. NY, FL, LA, CA). Same universal docs plus a one-page state notice/addendum and stricter execution flags.
> - `STATE_FORM` — states where we already author a native form (today: MS, TN). Offer the native form as default with the universal doc as companion.
>
> Seed `documentPath` from the matrix's UPOAA column and the flagged states, but make every field trivially editable — I will reclassify. Add a `documentPath` legend object (label + color + EN/ES description). Write a short unit test that asserts all 51 entries exist, tile coordinates are unique, and every `documentPath` is a valid enum value. Do not touch the UI yet.

### Prompt 2 — The tile-grid map

> Build the US tile-grid cartogram as the primary state selector, driven entirely by `src/data/states.ts`. Requirements:
> - Tile-grid layout (each state an equal square at its `tile` row/col), including a DC tile. Use CSS grid or SVG — your call — but it must be responsive and look right on mobile.
> - Color each tile by `documentPath` using the legend colors. Render a legend with the EN/ES descriptions.
> - Fully accessible: keyboard navigable (arrow keys + Enter/Space to select), visible focus ring, ARIA labels with the state name and its document path, adequate contrast and touch-target size. Treat this as a form control, not decoration.
> - On hover/focus, show the state name, financial + medical execution minimums, and any special triggers.
> - On select, set the chosen jurisdiction in app state and surface a clear "what you'll get" summary based on `documentPath`. Don't generate anything yet — just route the selection.
> - Bilingual EN/ES throughout, matching the existing language toggle.
>
> Keep it a self-contained component (`src/components/StateTileMap.tsx`) plus whatever hook holds the selection. Show me it running before wiring the engine.

### Prompt 3 — Engine routing

> Wire state selection into document generation. The selected jurisdiction's `documentPath` decides what the existing `pdf-lib` pipeline produces:
> - `UNIVERSAL` → universal financial POA + universal advance directive.
> - `UNIVERSAL_PLUS_ADDENDUM` → the two universal docs + a state addendum/notice page, and pass the state's `specialTriggers` into the execution-instruction sheet (e.g. burial/cremation needs extra witnesses).
> - `STATE_FORM` → the existing native template (`poa_ms` / `poa_tn`) as default, plus the universal doc as a companion.
>
> Refactor so adding a jurisdiction or changing a `documentPath` is a data edit in `states.ts`, never a new code branch. Routing builds a `RenderRequest` and calls the shared engine (`renderDocuments`); delivery is `downloadDocs` in the browser. No upload, no signed URLs, no storage, no server rate limit — client-side only. Add tests: each `documentPath` yields the expected set of documents.

### Prompt 4 — Universal templates + execution sheet

> Author the new bilingual (EN/ES side-by-side) markdown templates in the existing template format and tokenization scheme:
> - `poa_financial_universal.en-es.md` — UPOAA-based durable financial POA, with an explicit governing-law designation clause, durability language, and third-party-reliance + indemnity language so banks rely on it.
> - `ad_medical_universal.en-es.md` — advance directive + healthcare-agent designation (UHCDA-aligned).
> - `execution_instructions.en-es.md` — the signing sheet: sign before a notary AND two disinterested adult witnesses (neither the agent), keep originals with the binder; conditionally include any `specialTriggers` for the selected state.
> - `state_addendum.en-es.md` — a parameterized one-page state notice used by the `UNIVERSAL_PLUS_ADDENDUM` path.
>
> Keep `poa_ms` and `poa_tn` as fallbacks. After authoring, run the full `/free-plan` flow end to end for one UNIVERSAL state, one ADDENDUM state, and Mississippi, and show me the generated PDFs.
